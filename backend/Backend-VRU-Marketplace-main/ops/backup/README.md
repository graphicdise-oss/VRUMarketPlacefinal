# Backup — issue #21

**สคริปต์นี้ทำหน้าที่ตามที่ `docs/DECISIONS.md` §60/K1 ตัดสินไว้: cron บน host, `pg_dump` +
`tar` ของ volume ที่เก็บไฟล์อัปโหลด คู่กันในรอบเดียวกันเสมอ** — ดัมพ์แยกวันกันไม่ได้ เพราะแถวใน
`UploadedFile`/`PaymentSlip`/`RefundSlip`/`Shop.logoFileId`/`PaymentChannel.qrImageFileId` ต้องตรงกับ
ไฟล์จริงบนดิสก์เสมอ กู้คืนจากคนละวันจะได้แถวที่ชี้ไปยังไฟล์ที่ไม่มี (หรือกลับกัน)

**นี่คือส่วนที่ agent ทำแทนได้** — กลไก, การทดสอบกู้คืน, และเอกสารประกอบ ตามที่ตัดสินใจไว้ใน
`docs/DECISIONS.md` §60 (K1)

**สามข้อที่ [issue #21](https://github.com/graphicdise-oss/Backend-VRU-Marketplace/issues/21)
บอกว่า agent ตัดสินแทนไม่ได้ ตัดสินครบแล้ว 2026-09-21** (§67) — ปลายทางเป็น**ดิสก์ลูกที่สอง
ในเครื่องเดียวกัน** · **ไม่แจ้งเตือนอัตโนมัติ** ให้คนเข้ามารันเช็คเอง · สิทธิ์เข้าถึงปลายทาง
มีวิธีตั้งอยู่ในหัวข้อท้ายไฟล์แล้ว

⚠️ **issue ยังไม่ปิด เพราะยังไม่ได้ลงมือทำบนเครื่องจริง** — ต้องใส่ `BACKUP_DEST_DIR` จริง
ตั้งสิทธิ์โฟลเดอร์ ตั้ง cron และ**ลองกู้คืนจริงหนึ่งรอบ** ก่อนถึงจะนับว่าเสร็จ ·
ดูหัวข้อ "เหลืออะไรให้คนทำตอน deploy" ด้านล่าง

## ทำอะไรทุกรอบ

1. `pg_dump -Fc` ฐานข้อมูลทั้งฐาน ผ่าน `docker compose exec` เข้า container `postgres` โดยตรง
   (ไม่ต้องติดตั้ง `pg_dump` บน host — ใช้ตัวที่มากับ image เดียวกับที่รันจริง จึงรับประกันว่า
   เวอร์ชันตรงกันเสมอ)
2. `tar czf` ทั้ง named volume `uploads` ผ่าน container ชั่วคราว (`alpine`) ที่ mount volume
   นั้นแบบ read-only — ไม่หยุด container `api` ระหว่างสำรอง
3. เขียนทั้งสองไฟล์ลงโฟลเดอร์เดียวกันที่ตั้งชื่อด้วย timestamp เดียวกัน (`<UTC timestamp>/database.dump`,
   `<UTC timestamp>/uploads.tar.gz`) — **รอบเดียวกันเสมอ ไม่มีทางแยกกัน**
4. เช็คว่าทั้งสองไฟล์ไม่ว่างเปล่าก่อนถือว่าสำเร็จ — ล้มเหลวแล้ว **ไม่ทิ้งโฟลเดอร์ครึ่งๆ กลางๆ ไว้ให้
   ใครมากู้คืนแล้วเจอว่าใช้ไม่ได้ทีหลัง**
5. เขียนไฟล์ `latest-status` ที่ root ของปลายทาง — ตัวที่ให้ระบบเฝ้าดู (health check ภายนอก, cron
   monitoring) อ่านได้ว่ารอบล่าสุดสำเร็จเมื่อไหร่
6. ลบโฟลเดอร์ที่เก่ากว่า `RETENTION_DAYS` ทิ้ง (ค่าเริ่มต้น 30 วัน — เหตุผลด้านล่าง)

## ตั้งค่าก่อนใช้จริง

```bash
cp backup.env.example backup.env
# แก้ backup.env ให้ค่าจริง
```

| ตัวแปร | ต้องตั้งไหม | คืออะไร |
|---|:--:|---|
| `COMPOSE_PROJECT_DIR` | ✅ | path เต็มไปยัง repo นี้บนเครื่องจริง (ที่มี `docker-compose.yml`) |
| `BACKUP_DEST_DIR` | ✅ | **ตัดสินแล้ว 2026-09-21: ดิสก์ลูกที่สองในเครื่องเดียวกัน** (§67) — ใส่ mount point จริงของดิสก์ลูกนั้นตอน deploy · **ต้องเป็นคนละก้อนกับที่รัน Docker จริงๆ** ไม่ใช่แค่คนละโฟลเดอร์บนดิสก์เดียวกัน ไม่งั้นเท่ากับไม่มี backup เลย · เช็คด้วย `df /path/ปลายทาง` เทียบกับ `df /path/ที่รัน-docker` **ถ้าขึ้น device เดียวกัน แปลว่ายังผิดอยู่** |
| `RETENTION_DAYS` | ไม่บังคับ (default 30) | ดูเหตุผลด้านล่าง |
| `POSTGRES_DB` / `POSTGRES_USER` | ไม่บังคับ | ต้องตรงกับที่ตั้งใน `.env` ของแอปเอง |

### ทำไม 30 วัน

D5b เปิดข้อพิพาทได้ถึง **15 วัน**หลังร้านกดส่งของ และข้อพิพาทที่เปิดแล้วต้องมีเวลาให้แอดมินชุมชนตัดสิน
ต่ออีก — 30 วันเผื่อระยะทั้งสองส่วนไว้พร้อมกันโดยไม่ต้องคำนวณละเอียด (เผื่อเป็นสองเท่าของเพดานเปิด
ข้อพิพาท) **เป็นค่าเริ่มต้นทางวิศวกรรมที่ปรับได้ ไม่ใช่ตัวเลขที่ล็อกตายตัว** ถ้าเปลี่ยนใจ แก้ที่
`backup.env` บรรทัดเดียว ไม่กระทบข้อมูลเก่าที่อยู่ในปลายทางอยู่แล้ว

## รันด้วยมือ (ทดสอบ)

```bash
./backup.sh
```

## ตั้ง cron รันทุกวัน

```
0 3 * * * BACKUP_CONFIG_FILE=/opt/vru-marketplace/ops/backup/backup.env /opt/vru-marketplace/ops/backup/backup.sh >> /var/log/vru-marketplace-backup.log 2>&1
```

รันตอนตี 3 (เวลาไทย, ปรับ timezone ของ host เอง) — ช่วงที่คนใช้งานน้อยที่สุด

## รู้ได้ยังไงว่า backup พัง

```bash
./check-backup-health.sh              # เงียบ = ปกติ · exit 1 + ข้อความ = มีปัญหา
./check-backup-health.sh --verbose    # ให้มันพูดด้วยตอนปกติ (รันด้วยมือ)
```

**เงียบตอนปกติโดยเจตนา** — cron ส่งเมลทุกบรรทัดที่ job พิมพ์ออกมา ถ้ารอบที่ปกติก็ยังพิมพ์
คนจะชินแล้วเลิกอ่าน และการเตือนที่ไม่มีใครอ่านมีค่าเท่ากับไม่มีการเตือน

ตั้งคู่กับ cron ของ `backup.sh` โดยให้ตรวจหลังรอบสำรองจบไปแล้ว:

```
0 3 * * * BACKUP_CONFIG_FILE=/opt/vru-marketplace/ops/backup/backup.env /opt/vru-marketplace/ops/backup/backup.sh >> /var/log/vru-marketplace-backup.log 2>&1
0 9 * * * BACKUP_CONFIG_FILE=/opt/vru-marketplace/ops/backup/backup.env /opt/vru-marketplace/ops/backup/check-backup-health.sh
```

**ที่มันเช็คคือเจ็ดข้อนี้** — `backup.env` อ่านได้ · ปลายทางยังมีอยู่ (NAS ไม่ได้หลุด mount) ·
มีไฟล์ `latest-status` · รอบล่าสุดบอกว่า `OK` · mtime ยังไม่เกิน `MAX_AGE_HOURS` (default 36) ·
โฟลเดอร์ของรอบนั้นยังอยู่จริง · `database.dump` และ `uploads.tar.gz` ในโฟลเดอร์นั้นยังไม่ว่างเปล่า

**ทำไมต้องเปิดดูไฟล์จริงซ้ำ ไม่เชื่อข้อความ `OK` เฉยๆ** — ความพังที่น่ากลัวของระบบนี้ไม่ใช่
`backup.sh` crash (cron ส่งเมลให้อยู่แล้ว) แต่เป็นแบบเงียบ: NAS หลุด mount หรือกลายเป็น read-only
แล้วทุกรอบหลังจากนั้นเขียนลงโฟลเดอร์ว่างบนดิสก์เครื่องเดิม ซึ่งจากข้างนอกดูเหมือนสำเร็จทุกอย่าง

### ใครเป็นคนรู้ — **ตัดสินแล้ว 2026-09-21: ไม่แจ้งอัตโนมัติ ให้คนเข้ามารันดูเอง**

เจ้าของโปรเจคเลือกแบบนี้ (§67 ของ `docs/DECISIONS.md`) · แปลว่า **cron บรรทัดที่สองข้างบน
ไม่ต้องตั้งก็ได้** ให้เข้ามารัน `./check-backup-health.sh --verbose` ด้วยมือเป็นระยะแทน

⚠️ **ผลของการเลือกแบบนี้: ไม่มีใครรู้ว่า backup พังจนกว่าจะถึงวันที่ต้องใช้จริง** ซึ่งเป็นวันที่
แก้อะไรไม่ทันแล้ว — **ถ้าเลือกแบบนี้ ต้องตั้งใจเข้ามารันเองจริงๆ** ไม่ใช่ตั้งใจแล้วลืม

**ถ้าวันหนึ่งเปลี่ยนใจอยากให้มันเตือนเอง ไม่ต้องเขียนโค้ดเพิ่มเลยสักบรรทัด** — สคริปต์คืน
exit code 1 พร้อมข้อความทาง stderr อยู่แล้ว cron จึงส่งอีเมลให้เองถ้าใส่ `MAILTO` ไว้บนสุดของ
crontab แล้วตั้ง cron บรรทัดที่สอง:

```
MAILTO=someone@vru.ac.th
0 9 * * * BACKUP_CONFIG_FILE=/opt/vru-marketplace/ops/backup/backup.env /opt/vru-marketplace/ops/backup/check-backup-health.sh
```

รอบที่ปกติจะเงียบ จึงไม่มีเมลมากวน — เมลจะมาเฉพาะรอบที่มีปัญหาจริง

## กู้คืน

```bash
./restore.sh <BACKUP_DEST_DIR>/<timestamp ที่จะกู้>
```

**ดู `restore.sh` ก่อนรันจริงเสมอ** — สคริปต์นี้เขียนทับฐานข้อมูลและ volume ปัจจุบันทั้งหมด
(`pg_restore --clean` + เขียนทับไฟล์ในปลายทาง) ไม่มีการถามยืนยันซ้ำ ตั้งใจให้เป็นเครื่องมือของคน
ที่รู้อยู่แล้วว่ากำลังทำอะไร ไม่ใช่ปุ่มกดพลาดได้

## ทดสอบแล้วแค่ไหน — บอกตรงๆ

**คำสั่งหลักที่ทำงานจริง** (`pg_dump -Fc` / `pg_restore --clean --if-exists` / `tar czf` / `tar xzf`
รวมโฟลเดอร์ย่อย) **ทดสอบกู้คืนจริงแล้วบนเครื่องนี้**: ดัมพ์ฐาน `vru_marketplace` จริง (9 หมวดหมู่ + 6
บริษัทขนส่งจากข้อมูล seed) และไฟล์ตัวอย่าง 3 ไฟล์ (รวมไฟล์ในโฟลเดอร์ย่อย จำลองรูปร่างเดียวกับที่
`FileStorageService` เขียนจริง) → ลบฐานข้อมูลและลบโฟลเดอร์ทิ้งทั้งคู่ (จำลองดิสก์พัง) → กู้คืนทั้งสอง
กลับมา → **จำนวนแถวตรงเป๊ะ และ checksum ของทุกไฟล์ตรงกับต้นฉบับทุกบิต** ตาราง `_prisma_migrations`
ก็กลับมาครบ พิสูจน์ว่า `pg_restore` คืนทั้งสคีมาไม่ใช่แค่ข้อมูลแถว

**`check-backup-health.sh` ทดสอบครบทั้งแปดทางแล้ว** — ปกติ (เงียบ exit 0) · `--verbose` ·
ปลายทางหลุด mount · ไม่มี `latest-status` · รอบล่าสุดไม่ใช่ `OK` · เก่าเกิน `MAX_AGE_HOURS` ·
โฟลเดอร์ของรอบนั้นถูกลบไปแล้ว · ไฟล์ในโฟลเดอร์ว่างเปล่า — ทุกทางที่ควรล้มให้ exit 1 พร้อมข้อความ
ที่บอกว่าพังตรงไหน · **ตัวนี้ไม่ต้องใช้ Docker จึงทดสอบได้เต็มรูปแบบในสภาพแวดล้อมนี้**

**ส่วนที่ยังไม่ได้ทดสอบในสภาพแวดล้อมนี้**: การเชื่อมกับ `docker compose exec`/`docker run` จริง
(container resolution, การ resolve ชื่อ volume ที่ผูก prefix ของ compose project) — เครื่องที่ agent
รันอยู่ตอนเขียนสคริปต์นี้บล็อกการ pull image จาก Docker Hub ในระดับ network ทำให้ build/run
`docker-compose.yml` จริงไม่ได้ (`403 Forbidden` จาก registry) จึงทดสอบแค่คำสั่งแกนกลางตรงๆ กับ
Postgres และไฟล์ในเครื่องแทนที่จะผ่าน container จริง **ก่อนใช้งานจริงบนเครื่อง production ต้องรัน
`./backup.sh` แล้วตามด้วย `./restore.sh` เข้าฐานทดสอบหนึ่งรอบเต็มๆ ผ่าน `docker compose` จริงก่อนเสมอ**
(ตาม AC ของ #21 เองที่ขอให้ "ลองกู้คืนจริงหนึ่งครั้ง") — นี่ไม่ใช่ขั้นตอนที่ข้ามได้

## เหลืออะไรให้คนทำตอน deploy (ตาม AC ของ #21 เอง)

สามข้อที่ AC บอกว่า "agent ทำแทนไม่ได้" **ตัดสินครบแล้ว 2026-09-21** (§67) เหลือแต่ลงมือทำ
ตอน deploy จริง:

1. ✅ **`BACKUP_DEST_DIR`** — **ดิสก์ลูกที่สองในเครื่องเดียวกัน** · เหลือใส่ mount point จริง
   ตอน deploy และ**ยืนยันด้วย `df` ว่าเป็นคนละ device จริงๆ**
   · ⚠️ กันดิสก์พังได้ **แต่กันเครื่องหาย ไฟไหม้ หรือ ransomware ไม่ได้** — ดู §67
2. ✅ **ใครเป็นคนรู้ว่า backup พัง** — **ไม่แจ้งอัตโนมัติ ให้คนเข้ามารันดูเอง** ·
   วิธีเปลี่ยนใจทีหลังอยู่ในหัวข้อ "รู้ได้ยังไงว่า backup พัง" (ใส่ `MAILTO` บรรทัดเดียว)
3. ⏳ **สิทธิ์เข้าถึงปลายทาง backup — ยังต้องตั้งตอน deploy**

### สิทธิ์เข้าถึงปลายทาง backup — ต้องตั้งให้ถูกตอน deploy

ไฟล์ใน `BACKUP_DEST_DIR` **มีข้อมูลเหมือนฐานข้อมูลจริงทุกอย่าง** — สลิปโอนเงิน ชื่อผู้รับ
ที่อยู่ เบอร์โทร หลักฐานข้อพิพาท ครบ · **ใครอ่านโฟลเดอร์นี้ได้ ก็เท่ากับอ่านข้อมูลส่วนบุคคล
ของผู้ใช้ทั้งระบบได้** โดยไม่ต้องล็อกอินเข้าแอปเลย

ระบบตั้งใจให้สลิปเสิร์ฟผ่าน endpoint ที่ตรวจสิทธิ์เท่านั้น (invariant 9) — โฟลเดอร์ backup
ที่เปิดกว้างจะทำให้ด่านนั้นไร้ความหมาย เพราะข้อมูลเดียวกันหยิบไปได้จากอีกทาง

```bash
sudo chown root:root <BACKUP_DEST_DIR>
sudo chmod 700 <BACKUP_DEST_DIR>      # เจ้าของเท่านั้นที่เข้าได้ · คนอื่นบนเครื่องอ่านไม่ได้
ls -ld <BACKUP_DEST_DIR>              # ต้องขึ้น drwx------
```

**ข้อห้ามที่ต้องเช็คด้วย**

- **ห้ามวาง `BACKUP_DEST_DIR` ไว้ใต้ path ที่ Nginx เสิร์ฟ** ไม่ว่ากรณีใด
- **ห้ามใส่ใน Docker volume ที่ container อื่นอ่านได้** — ถ้าแอปถูกเจาะ backup จะติดไปด้วย
- ถ้าดิสก์ลูกที่สองถูก mount ไว้ให้คนอื่นใช้ร่วมด้วย (เช่น แชร์ไฟล์ในหน่วยงาน)
  **ต้องแยกโฟลเดอร์และสิทธิ์ให้ชัด** ไม่ใช่วางปนกับของคนอื่น
- **คนที่เข้าถึงได้ควรเป็นคนกลุ่มเดียวกับที่มีสิทธิ์ดูข้อมูลผู้ใช้อยู่แล้ว** ไม่ใช่ทุกคนที่มีบัญชีบนเครื่อง
  · ต้องสอดคล้องกับ privacy policy ของ [#22](https://github.com/graphicdise-oss/Backend-VRU-Marketplace/issues/22)
