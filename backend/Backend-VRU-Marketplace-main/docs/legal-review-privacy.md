## 1. 🔴 log การเข้าใช้ — พ.ร.บ.ว่าด้วยการกระทำความผิดเกี่ยวกับคอมพิวเตอร์ ม.26

**กฎหมาย**: ผู้ให้บริการต้องเก็บ**ข้อมูลจราจรทางคอมพิวเตอร์ไว้ไม่น้อยกว่า 90 วัน** นับแต่ข้อมูลเข้าสู่ระบบ
และเจ้าหน้าที่สั่งให้เก็บนานขึ้นได้ถึง 2 ปี · ประเภทข้อมูลที่ต้องเก็บกำหนดในประกาศกระทรวง ดีอี
(ฉบับปัจจุบันน่าจะเป็นปี 2564 — **ต้องตรวจ**)

**ระบบทำอะไรอยู่**: ตาราง `Session` **ตั้งใจไม่เก็บ IP และ user agent** (คอมเมนต์ใน `prisma/schema.prisma`
บอกว่า "ไม่มีอะไรในระบบที่ต้องใช้ จึงไม่ควรเก็บ") · repo ไม่มี config ของ Nginx · `docker-compose.yml`
ไม่ได้ตั้ง logging → **ตอนนี้ไม่มีอะไรรับประกันว่า log 90 วันมีอยู่จริง**

**ทำไมสำคัญ**: เหตุผลเดิมที่ไม่เก็บ ("ไม่มีใครใช้") ถูกต้องเมื่อดูแค่ PDPA แต่ถ้า ม.26 บังคับ
การเก็บก็มี**ฐานกฎหมายตาม PDPA ม.24(6)** (ปฏิบัติตามกฎหมาย) ทันที เหตุผลเดิมจึงใช้ไม่ได้อีกต่อไป

**คำถามถึงฝ่ายกฎหมาย**
1. แพลตฟอร์มนี้เป็น "ผู้ให้บริการ" ตามนิยามของ ม.3 และต้องเก็บข้อมูลจราจรประเภทไหนตามประกาศกระทรวง
2. log ของ Nginx (IP · เวลา · path) ที่เก็บ 90 วันพอไหม หรือต้องผูกกับ user id ด้วย

**ข้อเสนอทางเทคนิค (ถ้าต้องเก็บ)** — เก็บที่ **Nginx access log** แล้วหมุนเก็บ 90 วัน ดีกว่าเพิ่มคอลัมน์ใน DB:
ไม่ปนกับข้อมูลที่ต้อง anonymize ตาม G3 · ลบเองอัตโนมัติเมื่อครบกำหนด · **ต้องไม่มี query string ที่มี token**
(ลิงก์ยืนยันอีเมล/reset รหัสผ่านมี token อยู่ใน URL) · และต้องเพิ่มเรื่องนี้ในนโยบาย privacy ด้วย

## 2. 🔴 ผู้ใช้ที่ยังไม่บรรลุนิติภาวะ

**กฎหมาย**
- ป.พ.พ. ม.19: บรรลุนิติภาวะเมื่ออายุ **20 ปี** · ม.21: นิติกรรมของผู้เยาว์ที่ไม่ได้รับความยินยอมจากผู้แทนโดยชอบธรรม
  **เป็นโมฆียะ** (บอกล้างได้) ยกเว้นกิจการที่สมแก่ฐานานุรูปและจำเป็นในการดำรงชีพ (ม.24)
- PDPA ม.20: ถ้าอาศัย**ความยินยอม** กับผู้เยาว์ ต้องได้ความยินยอมจากผู้ใช้อำนาจปกครองด้วย
  (ยกเว้นกรณีที่ผู้เยาว์ทำได้เองตาม ป.พ.พ.) · **อายุไม่เกิน 10 ปี ต้องได้จากผู้ใช้อำนาจปกครองเท่านั้น**

**ระบบทำอะไรอยู่**: ไม่ถามอายุ ไม่เก็บวันเกิด · **ผู้ใช้หลักคือนักศึกษา ซึ่งส่วนหนึ่งอายุ 18–19 ปี**

**ผลกระทบ**: ฐานหลักของการประมวลผลข้อมูลในระบบคือ**สัญญา** (ม.24(3)) ไม่ใช่ความยินยอม ม.20 จึงกระทบน้อย
แต่**ตัวสัญญาซื้อขายและการเปิดร้าน**ของผู้เยาว์อาจถูกบอกล้างได้

**คำถามถึงฝ่ายกฎหมาย** — เลือกทางไหน:
- (ก) กำหนดอายุขั้นต่ำ 20 ปีใน ToS (ง่ายสุด แต่ตัดนักศึกษาปี 1–2 ออก)
- (ข) อายุต่ำกว่า 20 ต้องได้รับความยินยอมจากผู้ปกครอง (ติ๊กยืนยันในฟอร์ม)
- (ค) ผู้เยาว์ซื้อได้ แต่**เปิดร้านต้องอายุ 20 ปีขึ้นไป**

ร่าง ToS ข้อ 3 เขียนเผื่อไว้เป็นช่องว่าง `[ต้องตัดสิน]` · **ถ้าต้องมีการยืนยันอายุ ต้องแก้ backend เพิ่ม**

## 3. 🟠 สิ่งที่ PDPA ม.23 บังคับให้แจ้ง แต่นโยบายยังไม่มี

ม.23 ให้แจ้งเจ้าของข้อมูล**ก่อนหรือขณะเก็บ**: (1) วัตถุประสงค์ (2) ผลของการไม่ให้ข้อมูลเมื่อต้องให้ตามกฎหมาย/สัญญา
(3) ข้อมูลที่เก็บและ**ระยะเวลาเก็บ** (4) ผู้ที่อาจได้รับข้อมูล (5) ช่องทางติดต่อผู้ควบคุมข้อมูล/DPO (6) **สิทธิ์ของเจ้าของข้อมูล**

| ข้อที่ขาด | สิ่งที่ต้องเติม (จากโค้ดจริง) |
|---|---|
| **ฐานกฎหมายรายข้อ** (ม.24) | เพิ่มคอลัมน์ในตาราง "ข้อมูลที่เราเก็บ" — ส่วนใหญ่เป็น **สัญญา ม.24(3)** · `audit_log` / `disputeLostCount` / marker = **ประโยชน์โดยชอบ ม.24(5)** · log ตาม ข้อ 1 (ถ้ามี) = **หน้าที่ตามกฎหมาย ม.24(6)** · **ระบบไม่ได้ใช้ความยินยอม (consent) เป็นฐานหลัก** ควรเขียนให้ชัด เพราะการติ๊ก checkbox ตอนสมัครคือ "รับทราบนโยบาย" ไม่ใช่ "ให้ความยินยอม" |
| **ระยะเวลาเก็บ** | มีแล้วแค่ marker · ที่ต้องเพิ่ม: แจ้งเตือน **180 วัน** (L7) · backup **30 วัน** (`ops/backup`) · ไฟล์แนบแชทที่ไม่ได้ส่ง (`PENDING_CHAT_ATTACHMENT_TTL_HOURS`) · **ออเดอร์ แชท รีวิว audit_log = ตลอดอายุบัญชี / ไม่ลบ** ต้องเขียนเหตุผลให้ได้ ⚠️ `audit_log` ที่ไม่ลบเลยคือจุดที่ฝ่ายกฎหมายน่าจะถาม |
| **ผลของการไม่ให้ข้อมูล** | ไม่มีอีเมล = สมัครไม่ได้ · ไม่มีที่อยู่ = สั่งซื้อไม่ได้ · ไม่มีช่องทางรับเงิน = เปิดร้านรับเงินไม่ได้ |
| **สิทธิ์ครบทุกข้อ** | ตอนนี้พูดแค่สิทธิ์ลบ (ม.33) · ต้องเพิ่ม: เข้าถึง/ขอสำเนา (ม.30) · ขอรับ/โอนข้อมูล (ม.31) · คัดค้าน (ม.32) · ระงับการใช้ (ม.34) · แก้ไขให้ถูกต้อง (ม.35–36) · **ร้องเรียนต่อคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล (ม.73)** ⚠️ **ระบบยังไม่มีปุ่ม "ดาวน์โหลดข้อมูลของฉัน"** — คำขอตาม ม.30–31 ต้องทำด้วยมือผ่าน super admin (ใช้ได้ แต่ต้องเขียนขั้นตอนไว้ และตอบภายใน 30 วัน) |

## 4. 🟠 เจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคล (DPO) — ม.41

นโยบายเขียนว่า "มหาวิทยาลัยยังไม่ได้แต่งตั้ง" (§68) · แต่ ม.41(1) บังคับให้**หน่วยงานของรัฐตามที่คณะกรรมการประกาศ**
ต้องมี DPO และมหาวิทยาลัยราชภัฏเป็นหน่วยงานของรัฐ — **มีโอกาสสูงที่มหาวิทยาลัยมี DPO ระดับองค์กรอยู่แล้ว**
และมีนโยบายคุ้มครองข้อมูลส่วนบุคคลของมหาวิทยาลัยที่ระบบนี้ควรอ้างถึง

**สิ่งที่ต้องทำ**: ถามฝ่ายนิติการของมหาวิทยาลัยว่ามี DPO แล้วหรือยัง ถ้ามี ใส่ชื่อตำแหน่ง + อีเมลในนโยบาย
แทนที่ย่อหน้า "ยังไม่ได้แต่งตั้ง" · ถ้ามี **อีเมลของ DPO อาจเป็นคำตอบของช่อง `[ต้องเติม]` ที่ค้างอยู่ช่องเดียวได้เลย**

## 5. 🟠 ส่งข้อมูลไปต่างประเทศ — ม.28

**Brevo เป็นบริษัทฝรั่งเศส** อีเมลและเนื้อหาอีเมล (ชื่อสินค้า เลขออเดอร์ ผลข้อพิพาท) จึงออกนอกประเทศทุกครั้งที่ส่ง
· ม.28 ให้ส่งได้เมื่อประเทศปลายทางมีมาตรฐานเพียงพอ **หรือ**เข้าข้อยกเว้น เช่น จำเป็นเพื่อปฏิบัติตามสัญญากับเจ้าของข้อมูล

**สิ่งที่ต้องทำ**: (1) ให้ฝ่ายกฎหมายยืนยันว่าเข้าข้อยกเว้นข้อไหน (น่าจะเป็นข้อสัญญา) (2) **เขียนในนโยบายว่าข้อมูลถูกส่งไปต่างประเทศ**
ตอนนี้เขียนแค่ "ส่งผ่าน Brevo" (3) ตรวจว่าทำสัญญาประมวลผลข้อมูล (DPA) กับ Brevo แล้ว
— Brevo คือ**ผู้ประมวลผลข้อมูล**ตาม ม.40 ซึ่งบังคับให้มีข้อตกลงเป็นลายลักษณ์อักษร (Brevo มี DPA มาตรฐานให้เซ็น)

## 6. 🟠 แผนรับมือข้อมูลรั่ว — ม.37(4)

ต้อง**แจ้งสำนักงานคณะกรรมการฯ ภายใน 72 ชั่วโมง**นับจากรู้เหตุ (เว้นแต่ไม่มีความเสี่ยงต่อสิทธิ์)
และถ้าเสี่ยงสูงต้องแจ้งเจ้าของข้อมูลด้วย · repo ยังไม่มีเอกสารว่า**ใครรู้ ใครตัดสิน ใครแจ้ง**

**ข้อเสนอ**: เพิ่มหน้าสั้นๆ ใน `ops/` (เช่น `ops/incident/README.md`) บอกว่า ถ้า DB/backup/`.env` รั่ว →
ใครเป็นคนแจ้ง · เปลี่ยน secret ตัวไหน (**ยกเว้น `ACCOUNT_MARKER_PEPPER`** ตามที่นโยบายเตือนไว้แล้ว) ·
เพิกถอน session ทุกตัวยังไง · ต้องให้มหาวิทยาลัยกำหนดคนรับผิดชอบก่อน agent เขียนได้

## 7. 🟡 บันทึกรายการประมวลผล (ROPA) — ม.39

ผู้ควบคุมข้อมูลต้องมีบันทึกรายการ (ข้อมูลอะไร · วัตถุประสงค์ · ฐาน · ระยะเวลาเก็บ · ใครเข้าถึง · มาตรการรักษาความปลอดภัย)
· **ตาราง "ข้อมูลที่เราเก็บ" ในนโยบาย + คอลัมน์ฐานกฎหมายและระยะเวลาเก็บจากข้อ 3 = เกือบครบแล้ว**
ถ้ามหาวิทยาลัยมีแบบฟอร์ม ROPA กลาง ให้ใช้แบบนั้น

## 8. 🟡 ข้อความในนโยบายที่ผิดจากโค้ด (แก้ได้โดยไม่ต้องรอฝ่ายกฎหมาย)

| ในนโยบายเขียนว่า | โค้ดจริง |
|---|---|
| "คุกกี้สองใบ + **คุกกี้ที่สามสำหรับ CSRF**" | **ไม่มีคุกกี้ CSRF** — CSRF token ส่งทาง header (N8) · คุกกี้จริงมี 4 ใบ: `access_token` · `refresh_token` · `google_oauth_state` · `google_oauth_policy` (สองใบหลังอายุสั้น มีแค่ระหว่างล็อกอินด้วย Google) · ทุกใบจำเป็นต่อการทำงาน **จึงไม่ต้องขอความยินยอม** แต่ต้องบอกให้ถูก |
| หัวข้อ "ข้อมูลนี้ถูกส่งไปที่ไหน" มีแค่ Brevo | **ไม่ได้พูดถึง Google** — ล็อกอินด้วย Google ระบบ**ได้รับ**อีเมลและสถานะยืนยันอีเมลจาก Google (N2 · N15) ต้องบอกว่ารับอะไรมา |

⚠️ ตามคอมเมนต์ใน `src/legal/policy-version.ts` **แก้ข้อความนโยบายเมื่อไหร่ต้องเลื่อน `CURRENT_PRIVACY_POLICY_VERSION`
ใน commit เดียวกัน** · ผมจึง**ยังไม่แก้**ในรอบนี้ — แนะนำให้รวบข้อ 3, 5, 8 (และข้อ 1 ถ้าต้องเก็บ log)
เป็นการแก้ครั้งเดียว หลังฝ่ายกฎหมายตอบ จะได้เลื่อนเวอร์ชันแค่ครั้งเดียว

## 9. 🟡 พ.ร.ฎ.การประกอบธุรกิจบริการแพลตฟอร์มดิจิทัลที่ต้องแจ้งให้ทราบ พ.ศ. 2565

แพลตฟอร์มที่เป็นตัวกลางระหว่างผู้ขายกับผู้ซื้อเข้าข่าย "บริการแพลตฟอร์มดิจิทัล" · มีผลตั้งแต่ 20 ส.ค. 2566 ·
**เกณฑ์ที่ต้องแจ้ง ETDA** เท่าที่หาได้: รายได้ในไทยเกิน 1.8 ล้านบาท/ปี (บุคคลธรรมดา) หรือผู้ใช้เกิน 5,000 รายต่อเดือน
(**ต้องตรวจตัวเลขและเกณฑ์ของนิติบุคคล/หน่วยงานรัฐ**)

**ระบบนี้**: ไม่มีรายได้เลย (ไม่เก็บค่าธรรมเนียม — E3) · ผู้ใช้ช่วงแรกน่าจะต่ำกว่าเกณฑ์ · ผู้ให้บริการเป็นหน่วยงานรัฐ
→ **น่าจะยังไม่ต้องแจ้ง แต่ต้องให้ฝ่ายกฎหมายยืนยัน** โดยเฉพาะเมื่อผู้ใช้ต่อเดือนโตเกินเกณฑ์
· ถ้าต้องแจ้ง พ.ร.ฎ. นี้มีหน้าที่เรื่อง**ข้อตกลงการใช้บริการที่ชัดเจน**และช่องทางร้องเรียนด้วย — ร่าง ToS เผื่อไว้แล้ว

## ข้อที่เกี่ยวกับ ToS มากกว่า privacy (บันทึกไว้เผื่อฝ่ายกฎหมาย)

- **ผู้ขายต้องรับผิดชอบใบอนุญาตของตัวเอง** — อาหารแปรรูปต้องมี อย. · ยอดขายเกิน 1.8 ล้าน/ปี ต้องจดทะเบียน
  ตลาดแบบตรงกับ สคบ. (พ.ร.บ.ขายตรงและตลาดแบบตรง) · แพลตฟอร์มไม่ตรวจแทน แต่ ToS ต้องบอก
- **ห้ามขายออนไลน์ตามกฎหมาย** — เครื่องดื่มแอลกอฮอล์ (ประกาศคณะกรรมการควบคุมเครื่องดื่มแอลกอฮอล์ 2563) ·
  ผลิตภัณฑ์ยาสูบ (พ.ร.บ.ควบคุมผลิตภัณฑ์ยาสูบ 2560) · บุหรี่ไฟฟ้า · ยา — **หมวดหมู่ "เครื่องดื่ม" ใน L2 ต้องระวังเรื่องนี้**
- **แจ้งเตือนและนำเนื้อหาออก** (พ.ร.บ.คอมพิวเตอร์ ม.15 + ประกาศกระทรวงเรื่องขั้นตอนการแจ้งเตือน) — ผู้ให้บริการที่
  นำเนื้อหาผิดกฎหมายออกเมื่อได้รับแจ้งตามขั้นตอนไม่ต้องรับโทษ · **ระบบยังไม่มีปุ่ม "รายงาน"** ตอนนี้แจ้งผ่านแอดมินชุมชน/อีเมลได้
- **ข้อจำกัดความรับผิด** เขียนกว้างไม่ได้ — ป.พ.พ. ม.373 (ยกเว้นความรับผิดจากกลฉ้อฉลหรือประมาทเลินเล่ออย่างร้ายแรงเป็นโมฆะ)
  และ พ.ร.บ.ว่าด้วยข้อสัญญาที่ไม่เป็นธรรม 2540 (สัญญาสำเร็จรูปบังคับได้เท่าที่เป็นธรรม)
- **ข้อตกลงอิเล็กทรอนิกส์มีผล** — พ.ร.บ.ว่าด้วยธุรกรรมทางอิเล็กทรอนิกส์ 2544 ม.7–8 · แต่
  ~~⚠️ ระบบบันทึกการยอมรับแค่นโยบาย privacy ยังไม่บันทึกการยอมรับ ToS~~ → ✅ **บันทึกแล้วแบบ clickwrap ตั้งแต่ 2026-09-28 (§90)**
  · ยังไม่มีการขอให้บัญชีเดิมยอมรับฉบับใหม่เมื่อ ToS เปลี่ยน — เจ้าของเลือกทำทีหลัง
