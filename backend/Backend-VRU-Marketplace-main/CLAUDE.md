## Invariants

กฎที่ทุกฟีเจอร์ต้องเคารพ ถ้าโค้ดใหม่ขัดกับข้อไหน ให้หยุดและถามก่อนเขียนต่อ

### 1. Community กรองตอนอ่าน กั้นตอนเขียน

**ตอนอ่าน community เป็นตัวกรอง ไม่ใช่กำแพง** — ใครก็ดู ค้นหา และซื้อข้ามชุมชนได้
**ไม่ต้องเป็นสมาชิกชุมชน** `communityId` เป็นพารามิเตอร์ที่ client ส่งมาเพื่อกรองรายการร้านและสินค้า

**ดูและค้นหาไม่ต้องล็อกอิน · แต่ใส่ตะกร้าและสั่งซื้อต้องล็อกอิน + ยืนยันอีเมลแล้ว** (B0.1 · K4)
— "ข้ามชุมชนได้" พูดถึงการไม่ต้องเป็นสมาชิก ไม่ได้แปลว่าไม่ต้องมีบัญชี

**ตอนเขียนและตอนใช้สิทธิ์แอดมิน community คือกำแพง** — ทุก endpoint ของแอดมินชุมชนต้องผ่าน
**guard ตัวเดียวกัน** ที่เช็คสองชั้น:

1. ผู้เรียกมีแถวใน `CommunityAdmin` จริง
2. `communityId` ของแถวนั้นตรงกับ `Shop.communityId` ของเป้าหมาย

เขียนครั้งเดียวแล้วใช้ซ้ำ **ห้ามให้แต่ละ controller เช็คเอง** — controller มีวันลืม

**แอดมินชุมชนทำได้แค่ 7 อย่าง** ในชุมชนที่ super admin มอบหมายให้เท่านั้น: อนุญาตให้เปิดร้าน (**รวมตรวจการแก้ชื่อ/คำอธิบาย/โลโก้ของร้านที่อนุมัติแล้ว** · §86) ·
ระงับร้าน · อนุมัติ/ปฏิเสธรายการสินค้า (**รวมถอดสินค้าที่อนุมัติไปแล้ว** · §109) · ตัดสินออเดอร์ที่ถูกแช่แข็ง · ตัดสินข้อพิพาท ·
**ลบรีวิวที่ผิดกฎ** (ดู L3 · ต้องระบุเหตุผลและลง `audit_log` · เป็น soft delete) ·
**คุยกับร้านในชุมชนผ่านแชทแอดมิน↔ร้าน** (§106 · กล่องรวมของชุมชน · ทุกข้อความที่แอดมินส่ง/แก้/ยกเลิกลง `audit_log`)
**แก้ไขข้อมูล user ไม่ได้** สร้างชุมชนไม่ได้ ตั้ง–ถอดแอดมินไม่ได้ — สามอย่างหลังเป็นของ super admin เท่านั้น

**super admin ผ่านทุกด่านที่แอดมินชุมชนผ่าน** โดยไม่ต้องมีแถวใน `CommunityAdmin`
— **ยกเว้นเรื่องที่ตัวเองเป็นคู่กรณี** (ผู้ซื้อหรือเจ้าของร้านของเรื่องนั้น) ซึ่งทั้งแอดมินชุมชนและ super admin ตัดสินไม่ได้ (N28/N29)

**ทุกการกระทำของแอดมินต้องลง `audit_log`**

### 2. แพลตฟอร์มไม่เคยถือเงิน

ผู้ซื้อโอนตรงเข้าบัญชีร้าน ระบบไม่รู้ว่ามีเงินเข้าจริงหรือไม่ — รู้แค่ว่า **ร้านกดยืนยันว่าได้รับแล้ว**

- ไม่มี entity ชื่อ `Payment` มีแค่ `Shop.paymentChannels` — **เลขบัญชี/พร้อมเพย์ที่ร้านกรอกเอง
  + รูป QR ที่ร้านอัปเอง · ระบบไม่สร้าง QR ให้** (ดู K5)
- ฟิลด์บน order ชื่อ `sellerConfirmedAt` + `sellerConfirmedBy` — ห้ามใช้ชื่อ `paidAt` / `isPaid` เพราะสื่อว่าระบบยืนยันเอง
- **สลิปแนบในหน้าออเดอร์เท่านั้น ห้ามรับทางแชท** เพราะระบบต้องรู้ว่าสลิปใบไหนคู่กับออเดอร์ไหน
  ไม่มีการตรวจสอบสลิปอัตโนมัติ ร้านเป็นคนดูแล้วกดเอง
- **สลิปเป็นตารางแยก หลายแถวต่อออเดอร์** ไม่ใช่ฟิลด์ `slipUrl` ตัวเดียวบน `Order` —
  ผู้ซื้ออัปทับได้และต้องเก็บทุกใบไว้เป็นหลักฐาน (ดู I3) · ร้านปฏิเสธสลิปได้ไม่เกิน 2 ครั้ง (ดู I2)
- **ไม่เก็บค่าธรรมเนียมจากร้าน** เงินไม่ผ่านระบบจึงเก็บไม่ได้จริง ห้ามใส่ฟิลด์ค่าคอมมิชชันเผื่อไว้
- เงินเก็บเป็น `amount_minor` (สตางค์, integer) + `currency` — บาทอย่างเดียว

### 3. สต็อก: จองตอนสั่ง ตัดตอนร้านยืนยันเงิน

ช่วงระหว่างสั่งกับจ่ายยาวและไม่แน่นอน เพราะ**ตอนกดสั่งยังไม่รู้ยอดที่ต้องจ่าย** (ดูข้อ 4)
จึงต้องจองก่อน ตัดทีหลัง

- ตอนสร้าง order → สร้าง `StockReservation`
- ตอนร้านกดยืนยันเงินเข้า → ตัดสต็อกจริง
- **เรือนที่ 1 หรือ 2 หมดเวลา** → cron ยกเลิก order และคืนของ
- **เรือนที่ 3 หมดเวลาไม่ใช่การยกเลิก** — ตอนนั้นผู้ซื้ออัปสลิปแล้ว ยกเลิกฝ่ายเดียวไม่ได้
  cron จึงตั้งเป็น `REFUND_ORDERED` ให้ร้านคืนเงิน (ดู I1) · สต็อกยังไม่ถูกตัด จึงคืนของได้ตามปกติ
- **ตัดสต็อกไปแล้วแล้วออเดอร์ถูกยุติทีหลัง → ไม่คืนสต็อกอัตโนมัติ** ระบบไม่รู้ว่าของกลับมาถึงร้านจริงไหม
  แจ้งเตือนให้ร้านปรับเอง (ดู I7)

**นาฬิกาสามเรือนที่ต้องนับแยกกัน**

| # | ใครต้องทำ | ภายใน |
|---|---|---|
| 1 | ร้านใส่ค่าส่ง | 24 ชม. นับจากกดสั่ง |
| 2 | ผู้ซื้อโอน + อัปสลิป | 24 ชม. นับจากร้านใส่ค่าส่ง |
| 3 | ร้านยืนยันเงินเข้า | 3 วัน นับจากอัปสลิป |

**การจองต้องอยู่ยาวตั้งแต่เรือนที่ 1 จนจบเรือนที่ 3 — สูงสุดประมาณ 13 วัน**
(เส้นทางตรง 5 วัน + ร้านปฏิเสธสลิปได้ 2 ครั้ง ครั้งละ 4 วันตาม I2) และ**ถูกแช่แข็งยืดต่อได้อีกไม่จำกัด** ตาม H3

ห้ามตั้ง `expiresAt` ตัวเดียวสั้นๆ แล้วปล่อยหมดอายุกลางทาง ไม่งั้นร้านจะยืนยันเงินเข้าตอนที่ของถูกคนอื่นซื้อไปแล้ว
**และห้ามคำนวณวันหมดอายุครั้งเดียวตอนสร้างออเดอร์** — ต้องเลื่อนตามเรือนที่กำลังเดินอยู่จริง

ตัดสต็อกด้วย conditional update (`WHERE stock >= qty`) แล้วเช็คจำนวนแถวที่โดน ห้ามอ่านแล้วค่อยเขียนกลับ

**ตัดไม่สำเร็จเพราะของไม่พอ → ปฏิเสธการยืนยันทั้งใบ** บอกร้านให้ไปแก้สต็อกก่อน · ห้ามยืนยันครึ่งใบ
ห้ามปล่อยสต็อกติดลบ · **นาฬิกาเรือน 3 เดินต่อ ไม่หยุดให้** (ดู K8)

**สต็อกและราคาอยู่ที่ `ProductVariant` ไม่ใช่ `Product`**

### 4. Order ผูกกับร้านเดียว และค่าส่งมาทีหลัง

ร้านแต่ละร้านมีบัญชีของตัวเอง ผู้ซื้อจึงต้องโอนแยกต่อร้าน — checkout หนึ่งครั้งที่มีของ 3 ร้าน ต้องแตกเป็น 3 order

**ร้านเป็นคนใส่ค่าส่งหลังผู้ซื้อกดสั่ง** เพราะร้านแต่ละร้านใช้ขนส่งคนละเจ้า แพลตฟอร์มไม่รู้เรตของใครเลย
แปลว่า **ยอดรวมของ order ยังไม่มีค่าตอนสร้าง** — ห้ามออกแบบให้ `totalAmount` เป็น non-null ตั้งแต่แรก
ผู้ซื้อดูค่าส่งแล้ว**ปฏิเสธได้** ต้องระบุเหตุผล และออเดอร์ถูกยกเลิกทันที

### 5. ประวัติต้องไม่เปลี่ยนตามของปัจจุบัน

`OrderItem` เก็บ `priceAtPurchase` และ `productNameAtPurchase` ของตัวเอง แสดงผลใบเสร็จเก่าจากค่าที่ snapshot ไว้ ไม่ join ไปหา `Product`

**ที่อยู่จัดส่งก็ snapshot ลง order เหมือนกัน** ไม่เก็บแค่ `addressId` — ผู้ซื้อย้ายบ้านแล้วออเดอร์เก่าต้องยังแสดงที่อยู่เดิม
ลบที่อยู่เป็น soft delete

**ข้อยกเว้นเดียว: คำขอลบข้อมูลตาม PDPA** — snapshot มีชื่อผู้รับและเบอร์โทรอยู่บนนั้น การลบแถว `User`
จึงไม่ได้ลบอะไรเลย ตอนลบข้อมูลต้องเขียนทับ snapshot ด้วย (ดู G3 ใน `DECISIONS.md`)
นอกจากกรณีนี้ **ห้ามแตะ snapshot** ไม่ว่าด้วยเหตุผลอะไร

### 6. การมองเห็นสินค้าคุมสามชั้น

`shopPublishStatus` (ร้านคุม) และ `moderationStatus` (แอดมินคุม) สินค้าจะโชว์ต่อเมื่อผ่านทั้งคู่ ร้านแก้ของแอดมินไม่ได้

**ชั้นที่สามคือสถานะของร้าน** — ร้านถูกระงับ สินค้าหายจากรายการและหน้าค้นหาทันที
แต่ **ลิงก์ตรงยังเปิดได้พร้อมป้าย "ร้านนี้ถูกระงับชั่วคราว"** ไม่ใช่ 404
ไม่งั้นหน้าออเดอร์ของคนที่จ่ายเงินไปแล้วจะพังตามไปด้วย (ดู I14)
· **เจ้าของร้านถูกแบนบัญชี = ร้านหยุดขายแบบเดียวกัน** และลิงก์ตรงขึ้นป้ายเดียวกัน ไม่บอกคนนอกว่าบัญชีถูกแบน (§92) — อยู่ใน `LIVE_SHOP_FILTER` จุดเดียว

**ตัวร้านเองก็ต้องรออนุมัติก่อนเปิด** — `Shop.approvalStatus` เป็นคนละเรื่องกับ `Product.moderationStatus` ห้ามรวมกัน
· **เปิดแล้วแก้ชื่อ/คำอธิบาย/โลโก้ก็ต้องรอตรวจ** (`pending*` บน `Shop`) หน้าร้านโชว์ของเดิมระหว่างรอ และร้าน**ไม่หาย**จากรายการ (§86)

**สินค้าต้องอนุมัติทุกชิ้น และการแก้ไขแบ่งเป็นสองกลุ่ม**

- แก้ **ชื่อ / รูป / คำอธิบาย / หมวดหมู่** · **ชื่อ variant** · **เพิ่ม variant ใหม่**
  → กลับไป pending และหายจากหน้าร้านทันที
- แก้ **สต็อก / ราคา** · **ลบ variant** → ขึ้นทันที ไม่ต้องอนุมัติใหม่

ชื่อ variant อยู่กลุ่มแรกเพราะเป็นข้อความที่ผู้ซื้อเห็นและร้านพิมพ์เองได้อิสระ
ถ้าไม่ตรวจ ร้านจะย้ายของต้องห้ามไปซ่อนในชื่อตัวเลือกแทนชื่อสินค้า (ดู I13)

**การอนุมัติอยู่ที่ระดับ `Product` เสมอ ไม่ใช่รายตัว variant** — ตกหนึ่ง variant คือทั้งชิ้นกลับไป pending
· **รูปสินค้าเปิดสาธารณะได้เมื่อการอนุมัติครอบรูปนั้นแล้วเท่านั้น** (`product_image.approved_at` · §109) — รูปที่ยังไม่ตรวจเห็นแค่เจ้าของร้านกับแอดมินที่ตรวจได้

หมวดหมู่เป็นชุดกลางที่ super admin ดูแล ร้านพิมพ์เองไม่ได้

### 7. แบนแล้วต้องมีผลทันที

access token อายุสั้น และ guard ตรวจสถานะ user จาก DB — token ที่ออกก่อนโดนแบนต้องใช้ไม่ได้

แบนผู้ขาย / ระงับร้าน / **แบนผู้ซื้อ** → **ออเดอร์ที่ค้างถูกแช่แข็ง** ไม่ใช่ยกเลิกทิ้ง
ให้แอดมินชุมชนหรือ super admin ตัดสินทีละใบ — กลไกเดียวกันทั้งสามกรณี ห้ามเขียนโค้ดชุดที่สอง (ดู I10)

**แช่แข็งเป็นธง `Order.frozenAt` ไม่ใช่ค่าใน `Order.status`** เพราะปลดแล้วต้องกลับไปสถานะเดิม
และนาฬิกาเรือนเดิมต้องนับใหม่เต็มเวลา (ดู I6) · เรื่องเดียวกันกับข้อพิพาทที่เปิดค้างอยู่

**แอดมินเห็นออเดอร์ที่แช่แข็งได้แบบปิดบังเท่านั้น** — ไม่เห็นชื่อ ที่อยู่ เบอร์ และเปิดสลิปไม่ได้
เพราะคำถามที่ต้องตอบคือ "ปล่อยเดินต่อหรือยุติ" ซึ่งไม่ต้องใช้ข้อมูลส่วนตัว (ดู I5)
**break-glass มีทางเข้าทางเดียวคือข้อพิพาท** ห้ามเพิ่มทางที่สองผ่าน `frozenAt`

**ระงับร้าน = ห้ามขายใหม่ ไม่ใช่ห้ามทำของค้าง** (ดู J2) — ร้านที่ถูกระงับ **ยังกดส่งของ ยืนยันเงินเข้า
อัปสลิปคืนเงิน และตอบข้อพิพาทได้ตามปกติ** · ถ้าล็อกหมด คำสั่ง "ปล่อยเดินต่อ" ของ I4 จะไม่มีความหมาย
และร้านที่ถูกสั่งคืนเงินจะคืนไม่ได้จริง — กลายเป็นระบบที่ลงโทษผู้ซื้อแทนร้าน

**ออเดอร์ที่แช่แข็งพร้อมกับมีข้อพิพาทเปิดอยู่ → ข้อพิพาทเดินต่อตามปกติ** และคำตัดสินปลดการแช่แข็ง
ของใบนั้นไปในตัว (ดู J3)

### 8. ห้องแชทตรวจสิทธิ์ทุกครั้ง

ตรวจว่า user เป็นคู่สนทนาของห้องจริงทั้งตอน connect และตอน **reconnect**

**ห้องผูกกับคู่ (ผู้ซื้อ × เจ้าของร้าน) ไม่ใช่ผูกกับ `orderId` และไม่ใช่ผูกกับแถว `Shop`** —
ห้องเดียวต่อคู่ อยู่ยาวข้ามออเดอร์ **และข้ามการปิด-เปิดร้านตาม H12** (ดู K14)
คุยได้ตั้งแต่ก่อนมีออเดอร์ ห้ามออกแบบ schema ที่บังคับให้ทุกข้อความมี `orderId`

**แอดมินเห็นแชทได้เฉพาะตอนข้อพิพาทเปิดอยู่** guard ต้องเช็ค `Dispute.status === OPEN` สดๆ ทุกครั้ง
ไม่ใช่ flag ค้างไว้บน user · ลง `audit_log` ทุกครั้งที่เปิดดู — **ข้อนี้พูดถึงห้องผู้ซื้อ × เจ้าของร้าน**
· **แชทแอดมิน↔ร้าน (§106) เป็นคนละห้อง** ที่แอดมินเป็นคู่สนทนาเอง: ห้องเดียวต่อร้าน แอดมินของชุมชนร้านนั้น + super admin
เห็นร่วมกัน · ตรวจสิทธิ์สดทุก event เหมือนกัน · ถูกถอดจากชุมชนแล้วหลุดจากห้องทันที · **บัญชีแอดมินเปิดห้องผู้ซื้อใหม่ไม่ได้** (§105)

### 9. ที่เก็บ token และไฟล์ที่ตรวจสิทธิ์

- **access token และ refresh token อยู่ใน httpOnly cookie ทั้งคู่** ห้ามส่งกลับไปใน response body
  ต้องมี CSRF token คู่กัน · WebSocket ใช้ cookie ตอน handshake
- **ห้ามเอา input จาก user ไปประกอบ path ของไฟล์**
- สลิปและไฟล์ที่มีข้อมูลส่วนตัวเสิร์ฟผ่าน endpoint ที่ตรวจสิทธิ์เท่านั้น ไม่ใช่ path ที่ Nginx เปิดตรง

## ข้อจำกัดสภาพแวดล้อม

รันบนเซิร์ฟเวอร์มหาวิทยาลัยที่แรมจำกัด ผ่าน Docker Compose + Nginx

- ไม่ใช้ Redis — instance เดียว Socket.io adapter ในหน่วยความจำพอ
  · **cron ของนาฬิกาสามเรือนก็รันในโปรเซสเดียวกับ API** (`@nestjs/schedule`)
  ถ้าวันหนึ่งสเกลเป็นหลายอินสแตนซ์ ต้องเพิ่ม DB lock ไม่งั้นยิงซ้ำ
- ไม่ใช้ Elasticsearch — ค้นหาด้วย **`pg_trgm` + GIN index ของ PostgreSQL ไม่ใช่ `tsvector`** (ดู N5)
  · PostgreSQL ไม่มี text-search configuration ของภาษาไทย และภาษาไทยไม่เว้นวรรคระหว่างคำ
  `to_tsvector` จึงตัดชื่อสินค้าทั้งชื่อเป็นโทเคนเดียว · **ห้ามใช้ `to_tsvector` เปล่าๆ กับข้อความไทย**
  · **ใช้ `<%` (`word_similarity`) ไม่ใช่ `%` (`similarity`)** — `%` เทียบทั้ง string ชื่อสินค้าที่ยาว
  จะไม่ถึง threshold เสมอ แล้วการทนพิมพ์ผิดจะตายเงียบ
  · **เทสต์ค้นหาต้องใช้ข้อความไทยจริง** เทสต์ที่เขียนด้วยคำอังกฤษผ่านได้ทั้งที่ของพัง
  · ค้นชื่อสินค้า + ชื่อตัวเลือก + ชื่อร้านแบบทนพิมพ์ผิด · **คำอธิบายตรงตัวเท่านั้น** (`<%` กับข้อความยาวเจอทุกอย่าง · §110)
- pagination เป็น cursor-based
- **ไฟล์อัปโหลดเก็บบนดิสก์ของเซิร์ฟเวอร์ผ่าน Docker volume** (ดู K1) ไม่ใช้ object storage
  · ยังต้องเสิร์ฟผ่าน endpoint ที่ตรวจสิทธิ์ ห้ามให้ Nginx เปิด path ตรง
  · **นี่เป็นข้อที่สามที่ผูกระบบไว้กับอินสแตนซ์เดียว** คู่กับ cron และ Socket.io adapter
- ไฟล์อัปโหลดต้อง re-encode เพื่อลบ EXIF (รูปจากมือถือมีพิกัด GPS ติดมา)
  · **route อัปโหลดทุกเส้นใช้ `@AcceptsUpload({ field, maxFiles?, check })` เท่านั้น ห้ามใช้ `FileInterceptor` ตรงๆ** (§100)
  — รวมเพดานต่อบัญชี + การตรวจสิทธิ์ก่อนอ่าน body (`check` เรียกเมธอดเดียวกับที่ service เรียกเอง) · ไฟล์รอบนดิสก์
  ไม่ใช่หน่วยความจำ · การแปลงรูปผ่าน `ImageProcessingGate` เสมอ (ใน `FileStorageService`)
  · รูปสินค้าสูงสุด 10 รูป · 10MB ต่อรูป · รูปรีวิวสูงสุด 5 รูป · แชท 1 รูป/ข้อความ **jpg/png เท่านั้น**
- ส่งอีเมลผ่าน **Brevo หรือ SMTP (เช่นอีเมลของมหาวิทยาลัย) เลือกด้วย `EMAIL_TRANSPORT`** (§107) โดยโค้ดต้องอยู่หลัง interface `EmailSender` ตัวเดียว
  · ต่อ SMTP ต้องมี TLS เสมอ ห้ามส่งรหัสผ่านโดยไม่เข้ารหัส · **ห้ามเอาข้อความตอบกลับของ SMTP/ข้อความ error ลง log** (มักมีอีเมลผู้รับ · §104)
- มีตารางอ้างอิง จังหวัด → อำเภอ → ตำบล + รหัสไปรษณีย์ เป็น seed data

แอดมิน**เปิดร้านไม่ได้ แก้หน้าร้านไม่ได้ ใส่ตะกร้า/สั่งซื้อไม่ได้** (`@RefusesAdmins()` · หน้าร้านเพิ่มใน §87) · คนที่ยังมีร้านเปิดอยู่**แต่งตั้งเป็นแอดมินไม่ได้**

และเพราะ SUPER_ADMIN ตั้งผ่าน DB โดยไม่มีโค้ดเช็ค

> ~~`Membership`~~ ถูกตัดทิ้งแล้ว **ห้ามสร้างกลับมา** — หลังตกลงว่าไม่ต้องเป็นสมาชิกก็ซื้อได้
> และ 1 คน = 1 ร้าน แถวของผู้ขายจะซ้ำกับ `Shop` ทุกแถวโดยไม่ให้ข้อมูลเพิ่ม

## กฎการทำงาน

- **ทำทีละหัวข้อแล้วหยุดรายงาน** เจ้าของโปรเจคต้องตรวจก่อนไปต่อ
- **ห้าม `git push` โดยไม่ถามก่อน** — commit ในเครื่องได้ตามปกติ แต่ต้องแจ้งและรอคำตอบก่อน push ทุกครั้ง
- **แตะเฉพาะไฟล์ที่เกี่ยวกับหัวข้อที่ทำอยู่** เจอที่อื่นที่ควรแก้ ให้เขียนบอกไว้ในรายงาน แล้วปล่อยไว้ก่อน
  — diff ที่มีของแถมทำให้คนตรวจแยกไม่ออกว่าอะไรคือของจริง
- **ทุกครั้งที่หยุดรายงาน ต้องบอกสามอย่าง**: แก้ไฟล์ไหนบ้าง · เปลี่ยนพฤติกรรมอะไร ·
  **กระทบใครบ้าง** (frontend / migration ที่ต้องรัน / ข้อมูลเดิมที่ต้องแปลง)
- **`docs/PROGRESS.md` คือ source of truth ว่าทำถึงไหนแล้ว** อย่าเดาจาก git log · ปิดหัวข้อเมื่อไหร่
  ต้องอัปเดตที่นั่น
- **แตะ endpoint / response shape / error code เมื่อไหร่ ต้องอัปเดต `docs/FRONTEND-NOTES.md` ทันที**
  ไม่ใช่รอสะสมไปทำทีเดียวตอน handoff
- เอกสารใน `docs/` เป็นภาษาไทย · คอมเมนต์ในโค้ดและ commit message เป็นภาษาอังกฤษ
- commit message อธิบาย **ทำไม** ไม่ใช่แค่ **ทำอะไร**

### ไม่รู้ = หยุดถาม ห้ามเดา

**ไม่มั่นใจเรื่องอะไรก็ตาม ห้ามเดาแล้วเขียนต่อ** — โค้ดที่เดาถูกบ้างผิดบ้างแก้ยากกว่าการถามหนึ่งคำถาม
โดยเฉพาะเมื่อมันไปฝังอยู่ใน schema หรือ API contract แล้ว

**แต่แยกให้ออกระหว่างสองอย่างนี้**

| ไม่มั่นใจแบบไหน | ทำยังไง |
|---|---|
| **หาคำตอบเองได้** — ตารางนี้มีคอลัมน์อะไร ฟังก์ชันนี้ทำอะไร endpoint นี้ตอบอะไร ของเดิมเขียนไว้ยังไง | **ไปหาคำตอบเอง** อ่านโค้ด อ่าน migration รันดูจริง แล้วค่อยเขียน — อย่าถามสิ่งที่เปิดไฟล์ดูก็รู้ |
| **มีแต่เจ้าของโปรเจคที่ตอบได้** — business rule, ตัวเลขที่ไม่ได้เขียนไว้ที่ไหน, เคสที่ตีความได้หลายทาง, จะทำ A หรือ B ที่ให้ผลต่างกัน | **หยุดแล้วถาม** พร้อมเสนอตัวเลือกเป็นข้อๆ และบอกว่าแนะนำอันไหนเพราะอะไร |

**ช่องว่างที่เคยอยู่ตรงนี้ปิดหมดแล้ว 2026-09-11** — คำตอบอยู่ที่ H1–H12 และ I1–I18 ใน `DECISIONS.md`

**เจอช่องว่างใหม่ให้ถาม แล้วเขียนคำตอบลง `DECISIONS.md`** มันมีหน้าตาสามแบบ:

- สองข้อที่ตัดสินไปแล้วชนกันเอง และไม่มีที่ไหนบอกว่าข้อไหนชนะ
- สถานะหนึ่งเจอเหตุการณ์ที่ไม่เคยเขียนไว้ว่าจะไปต่อทางไหน
- ตัวเลขที่โค้ดต้องใช้ แต่ไม่มีใครเคยพูดถึง (เพดานเวลา จำนวนครั้ง ระยะหมดอายุ)

**ถ้าจำเป็นต้องเดาจริงๆ เพราะติดต่อไม่ได้** — ทำส่วนที่ไม่ขึ้นกับคำตอบให้เสร็จก่อน แล้ว
**เขียนให้ชัดว่าเดาอะไรไว้บ้างและเดาบนสมมติฐานอะไร** ทั้งในรายงานและใน Decision Log ของ `PROGRESS.md`
ห้ามเงียบแล้วปล่อยให้เจ้าของโปรเจคมาเจอเองทีหลัง

## กฎการเขียนโค้ด

### ESM ล้วน · `.js` ต่อท้าย relative import ทุกอัน (N6)

**NestJS 12 เป็น ESM ล้วน** ไม่มี CommonJS build ผลคือ:

```ts
import { HealthService } from './health.service.js';   // ✅ ไฟล์จริงเป็น .ts
import { HealthService } from './health.service';      // ❌ typecheck ผ่าน แต่บูตไม่ขึ้น
```

TypeScript ไม่เติมนามสกุลให้ตอน emit · **ลืมแล้วจะพังตอนรัน ไม่ใช่ตอน compile**
· นี่เป็นแบบเดียวกับที่ `nest new` ของ CLI v12 generate ออกมา ไม่ใช่ท่าเฉพาะของโปรเจคนี้

**ตัวแปร env ที่เป็นตัวเลขต้องประกาศชนิด** — `PORT: number = 3000` ไม่ใช่ `PORT = 3000`
ไม่งั้น metadata เป็น `Object` แล้ว `class-transformer` ไม่แปลงค่าที่ได้มาเป็น string (ดู N6)

### ทุก module หน้าตาเหมือนกัน

`module` / `controller` / `service` / `dto` ตามแบบมาตรฐานของ NestJS
ไม่มี module ไหนคิดโครงสร้างของตัวเองขึ้นมาใหม่ · ดู `src/health/` เป็นตัวอย่าง

**`*.spec.ts` ไม่ได้อยู่ข้าง module — อยู่ใน `test/` ทั้งหมด** เพราะ M5 ไม่มีเทสต์ชั้น service
เทสต์ทุกใบเข้าทางขอบของแอปจริง จึงไม่มีเหตุให้ไปวางไว้ข้างไฟล์ที่มันไม่ได้เรียกตรงๆ

**ตัวรันเทสต์คือ Vitest ไม่ใช่ Jest** (`npm test`) · config เดียว ไม่มีไฟล์ config สำหรับ e2e แยก
· ใช้ `vi.spyOn` ไม่ใช่ `jest.spyOn`

**service ไม่รู้จัก `req` / `res`** รับพารามิเตอร์ธรรมดา คืนค่าธรรมดา โยน exception ของ domain
— controller เป็นชั้นเดียวที่แปลงเป็น HTTP

### ทุก route ต้องล็อกอินก่อน เว้นแต่เขียนว่าไม่ต้อง (#24)

**`AuthGuard` เป็น global guard แบบ default-deny** — route ใหม่ที่เขียนขึ้นมาถูกกั้นไว้ก่อน
ถ้าอยากให้เปิด ต้องใส่ **`@Public()`** ซึ่งเป็นบรรทัดที่เห็นใน diff · ทางกลับกัน (ต้องใส่ decorator
เพื่อ*ปิด*) คือท่าที่มีวันลืม และของที่ลืมคือ route ที่ควรต้องล็อกอิน

- **`@Public()` ไม่ได้แปลว่าไม่มีผู้ใช้** guard ยัง resolve session ให้ถ้ามี cookie
  — หน้ารายการสินค้าที่ดูได้โดยไม่ล็อกอิน (invariant 1) แต่อยากรู้ว่าคนดูเป็นใคร ใช้ข้อนี้
  · อ่านด้วย `readSession(request)` แล้วจัดการเคส null เอง
- **`@Public()` ไม่ยกเว้น CSRF** — POST/PATCH/DELETE ต้องมี header `x-csrf-token` ทุกเส้น
  **ไม่มีรายการยกเว้น** (รายการยกเว้นคือรายการที่มีคนเติม)
- **`@CurrentUser()` ใช้ได้เฉพาะ route ที่ไม่ public** ให้ `{ id, email, role, emailVerified }`
  ที่**อ่านจาก DB มาในรีเควสต์นั้น** ไม่ใช่ค่าที่แกะจาก token (invariant 7)
- **ห้ามเขียน guard ตัวที่สองที่อ่าน cookie เอง** — หัวข้อ 11 ใช้ `SessionService` ตัวเดียวกันนี้
  ตอน WebSocket handshake · guard ของแอดมินชุมชน (หัวข้อ 3) ต่อยอดจาก `CurrentUser` ไม่ใช่จาก cookie

### rate limit เป็น opt-in ตรงข้ามกับ auth (#28)

**`@RateLimited('ชื่อกฎ')`** แปะเฉพาะ route ที่เดาหรือสแปมได้ · route ใหม่ไม่มีเพดานจนกว่าจะแปะ
— ตรงข้ามกับ `@Public()` โดยเจตนา เพราะ route ที่ลืมแปะคือ route ที่เปิดโล่ง ส่วน route ที่ถูกแปะ
ทั้งที่ไม่ควรคือ route ที่พังตอนคนใช้จริง และไม่มีใครมานั่งเฝ้า

- **เพิ่มกฎใหม่ที่ `src/auth/rate-limit.policy.ts`** ที่เดียว · ตัวเลขทุกตัวอ่านจาก env มี default
- **นับต่อ (IP + อีเมล) เป็นค่าตั้งต้น** — คนจำนวนมากอยู่หลัง IP เดียวกันได้พร้อมกัน
  (มือถือผ่าน CGNAT · wifi สาธารณะ · router สำนักงาน) นับแต่ IP คือคนเดียวยิงรัวแล้วล็อก
  ทุกคนที่อยู่หลัง IP นั้นออกไปด้วย
- **นับต่อ IP อย่างเดียวได้สองกรณี และต้องตั้งเพดานหลวมกว่าเสมอ**
  1. request นั้น**ไม่มีอีเมลให้นับ** (เช่น `password/reset` ที่มีแต่ token)
  2. เป็น**ชั้นที่สองซ้อนบนชั้น (IP + อีเมล)** ในเส้นที่คนร้าย**เปลี่ยนค่าอีเมลในฟิลด์ได้ฟรี**
     ไม่ว่าจะเป็นอีเมลที่ตัวเองคิดขึ้นมาใหม่ทุกครั้ง (สมัครสมาชิก) หรืออีเมลของเหยื่อที่ตัวเองแค่ลองยิง
     (ล็อกอินแบบ credential stuffing) — ทั้งสองเส้นเข้าข้อนี้ (ดู N18) **ห้ามใช้ข้อนี้แทนชั้นแรก
     ต้องซ้อนเท่านั้น**
- **นับต่อบัญชีได้เฉพาะ route ที่ต้องล็อกอิน** (key `'account'` · §100) — เมื่อสิ่งที่จำกัดคือการใช้งานของบัญชีนั้นเอง
  เช่นอัปโหลด · ไม่ใช่ทางเลี่ยงข้อ (IP + อีเมล) ของเส้นที่ยังไม่ล็อกอิน
- **ห้ามล็อกบัญชีถาวรไม่ว่ากรณีใด** (I17) — เพดานทุกตัวเป็นหน้าต่างที่เปิดเองเมื่อครบเวลา
- **ถูกจำกัดแล้วต้องส่ง header `Retry-After` เป็นจำนวนวินาทีจริง** (RFC 9110 §10.2.3)
  คำนวณจากตัวนับที่นับตาม (IP + อีเมล) เดียวกับที่ตัดสินใจปฏิเสธ ไม่ใช่เลขคงที่ ·
  ปลอดภัยเพราะนับตามสิ่งที่ถูกลอง ไม่ใช่ตามว่าบัญชีมีจริงไหม — เลขจึงไม่เฉลยอะไรที่ I16 ปิดไว้
- ⚠️ **ตัวนับอยู่ในหน่วยความจำของโปรเซส = ข้อที่สี่ที่ผูกระบบไว้กับอินสแตนซ์เดียว**
  คู่กับ cron · Socket.io adapter · ไฟล์อัปโหลด

### validate ที่ขอบ ไม่ใช่กลางทาง

ทุก input จากภายนอกผ่าน DTO + **`class-validator`** (ตัดสินแล้วใน K3 · **ไม่ใช้ Zod**) **ที่ชั้น controller**
เลยเข้ามาแล้วถือว่าข้อมูลสะอาดและมี type จริง

**error response ใช้รูปแบบเดียวทั้งระบบ** ตั้งแต่ endpoint แรก — frontend เขียน error handler ครั้งเดียวจบ
กลับไปแก้ทีหลังแปลว่าต้องแก้ทั้งสองฝั่งพร้อมกัน
· รูปร่าง: **`code` (อังกฤษ) + `message` (ไทย โชว์ได้เลย) + `fieldErrors`** ตาม L4
· **ใช้รูปแบบเดียวกันกับ error ที่ออกทาง WebSocket ด้วย**

**รูปแบบ API ที่ล็อกแล้ว** (ดู M1–M3 · เปลี่ยนทีหลังต้องแก้ทั้งสองฝั่งพร้อมกัน)

- ทุก path ขึ้นต้น **`/api/v1/`**
- JSON เป็น **`camelCase`** ทั้งขาเข้าและขาออก · **ชื่อคอลัมน์ใน DB เป็น `snake_case`**
  ให้ Prisma แปลงด้วย `@map` · **ห้ามให้ชื่อคอลัมน์รั่วออกไปใน response**
- response ที่เป็นรายการใช้ซอง **`{ items, nextCursor, hasMore }`** · ไม่มี `total`
- **เอกสาร API สร้างจาก DTO ด้วย `@nestjs/swagger` ห้ามเขียน `api.md` ด้วยมือ** (M4)

### เขียนให้ปลอดภัยโดยตั้งใจ

- **log เฉพาะสิ่งที่โชว์ในที่สาธารณะได้** — ห้ามมี token, รหัสผ่าน, เลขบัญชี, สลิป, ที่อยู่, เบอร์โทร ใน log
- query ผ่าน Prisma เสมอ · ถ้าจำเป็นต้องใช้ raw SQL ให้ใช้ `$queryRaw` แบบ parameterized
- endpoint ที่เดารหัสผ่านหรือสแปมได้ (ล็อกอิน สมัคร ขอลิงก์ยืนยัน) ต้องมี rate limit
- **ความลับอยู่ใน `.env` และมี `.env.example` ที่ไม่มีค่าจริง** — ห้าม commit ค่าจริง
- error ที่ส่งกลับไปหา client บอกแค่ว่าผิดอะไร ไม่บอก stack trace หรือชื่อตาราง

### คอมเมนต์อธิบายว่า *ทำไม*

โค้ดบอกอยู่แล้วว่ามันทำอะไร คอมเมนต์จึงมีค่าเมื่อบอกสิ่งที่โค้ดบอกไม่ได้ —
ทำไมถึงเลือกทางนี้ ทำไมถึงมีเงื่อนไขแปลกๆ ตรงนี้ อ้างอิงข้อไหนใน `DECISIONS.md`

ตั้งชื่อตัวแปรและฟังก์ชันให้อ่านแล้วเข้าใจ จะได้ไม่ต้องคอมเมนต์อธิบาย

### ของที่เปลี่ยนทีหลังแล้วเจ็บ

**Migration เขียนแล้วห้ามแก้ไฟล์เดิม** คนที่รันไปแล้วมี state ที่ขึ้นกับของเดิม ให้เพิ่มไฟล์ใหม่แทน

**สี่ข้อนี้ล็อกแล้ว เปลี่ยนแปลว่าต้อง migrate ข้อมูลย้อนหลัง — ต้องคุยกับเจ้าของโปรเจคก่อนเสมอ**

| ข้อ | ค่าที่ล็อก |
|---|---|
| id | **UUIDv7** ทุกตาราง |
| เวลา | **`TIMESTAMPTZ` เก็บ UTC** แปลงเป็นเวลาไทยตอนแสดงผล |
| เงิน | **`amount_minor` (สตางค์, integer) + `currency`** |
| ลบข้อมูลตาม PDPA | **anonymize ทั้ง `User` และ snapshot บนออเดอร์ · ห้าม `DELETE` แถวทิ้ง** เพราะ FK ต้องยังอยู่ |

ชื่อฟิลด์ในข้อ 2 (`sellerConfirmedAt` ไม่ใช่ `paidAt`) และข้อ 3 (สต็อกอยู่ที่ variant) ก็ล็อกเหมือนกัน
**ขัดข้อไหนให้หยุดถามก่อน**
